Intent

01

From understanding an algorithm to building its system.

This prototype is a preliminary project for my thesis. Its purpose is to develop practical knowledge of how to build a real ANC system, providing a foundation for a more ambitious thesis project.

After studying and simulating active noise control in my ANC Practice Library, I started this demonstrator to carry that work into hardware. The process connects algorithm implementation, audio electronics, acoustic measurements, and design decisions shaped by the microcontroller’s timing and memory limits.

The target is a single-channel feedforward ANC demonstrator. A reference microphone senses the disturbance, an error microphone monitors the target location, and an adaptive filter will drive a control loudspeaker to reduce the residual sound there.

This makes the project an exercise in both DSP and implementation: the filter equations have to coexist with audio formats, peripheral timing, acoustic propagation, memory limits, and a deadline for every block.

Architecture

02

A small platform with direct control of the audio path.

Acquisition
Two INMP441 MEMS microphonesReference and error channels, with 24-bit PCM carried over I2S.
Processing
STM32F446RE on a NUCLEO boardCortex-M4F at a nominal 168 MHz, with 128 KiB RAM.
Output
PCM5102 DAC, TDA amplifier, and loudspeakerThe DAC converts the I2S output for the amplifier and control loudspeaker.

Firmware

C and register-level audio configuration

The audio peripherals and DMA are configured directly through MCU registers. The application runs without an RTOS. DMA interrupts flag completed buffer halves for handling in the main loop.

Scheduling

Continuous I/O, processing in blocks

Circular DMA moves audio while the CPU handles completed blocks. The current transport uses 48 stereo frames per half-buffer: a nominal 1 ms processing interval at 48 kHz.

DSP

Block FxLMS with CMSIS-DSP

The C kernel includes adaptive filtering, acoustic feedback compensation, overlap-save secondary-path filtering, and FFT-based coefficient updates.

Connecting measurements to firmware

Use the measured acoustic paths.

I measured the control speaker’s paths to both microphones using REW and a Focusrite interface. The export workflow turns those impulse responses into float32 C coefficients, preserving their arrival times and relative gain through a common electrical loopback correction. The linked firmware coefficients were checked against the exported arrays.

Current progress

03

The next step is reducing the PCM processing rate.

The audio path works in passthrough, the FxLMS code is implemented, and measured acoustic models are loaded into the firmware. The controller has also been run on the STM32 in a separate benchmark.

Those tests showed that the current implementation takes too long to process the measured models at 48 kHz. The next step is to reduce the processing rate before integrating and testing adaptive cancellation in the live audio loop.

Next step

Downsample the MEMS PCM for the controller.

Keep I2S input and output at their nominal 48 kHz rate, filter and decimate both microphone signals, run FxLMS at a lower rate, then interpolate its output for the DAC. The first candidate is 8 kHz. The final choice will depend on the control band, processing cost, and added filter delay.

Both microphone channels need synchronized conversion with separate filter states. The complete chain must then be timed, its effective acoustic paths re-identified, and its latency checked before enabling live adaptation.

What remains before a cancellation demonstration

  1. Implement and validate anti-alias filtering, decimation, and output interpolation.
  2. Benchmark the complete chain, then revisit the acoustic models and geometry with the new latency.
  3. Integrate the controller into live DMA audio and measure the residual error with adaptation enabled.
